# リアルタイム解像度グリッド実測(2026-09-10)

フルグリッド実測: 10解像度 × 16/20/24fps × 4/8step × t2av/a2v。
元データ(`/tmp/claude-1000/ltx_grid_*.json` と HTML 表)は tmp 消去で失われたため、
保存済みの表画像から本ファイルへ転記して恒久保存する(2026-09-13)。

## 測定条件

- 2026-09-10 実測 / 環境はレポート([acceleration-report-20260910.md](acceleration-report-20260910.md))と同一: **RTX PRO 6000 Blackwell 96GB(sm_120)**、torch 2.11.0+cu130
- フル構成: `LTX25_TRANSFORMER_PRECISION=nvfp4` + `OFFLOAD_MODE=none` + `LTX25_CUDA_GRAPH=1` + `LTX25_NVENC_PRESET=p4`(= gateway プリセット `nvfp4-fast`)
- 約5秒クリップ。予算 = 再生時間: 16fps=81f/5.06s、20fps=97f/4.85s、24fps=121f/5.04s
- ウォーム測定(CUDA Graph capture 済み。**初回は shape ごとに +1〜3.6s** 上乗せ)
- 括弧内はリアルタイム比(生成時間 ÷ 再生時間)。**太字 = 1.0x ギリギリ(〜0.99x)**、~~取り消し~~ではなく **超** 印 = 1.0x 超過、「—」 = t2av が既に超過のため a2v は未測定

> **【注意】現行 GPU(RTX PRO 5000 48GB、2026-08-07 交換後)では約 +30〜45% を見込むこと。**
> 2026-09-13 実測: a2v 512×384 相当@16fps・4step が 2.90s(表の 2.22s に対し +31%)、8step が 4.48s(表の 3.10s に対し +45%)。
> 表の相対関係(解像度・fps・step 間の比)はそのまま使えるが、1.0x 境界は 1〜2 段下の解像度に下がる。

## 追補: RTX PRO 5000 48GB 実測(2026-09-13)

1024×768(79万画素)@24fps・121f(予算5.04s)、同フル構成(nvfp4-fast)・upscaleなし・VAEデコード・seed 1004。
ウォーム2回の平均(初回はcapture費 — この巨大shapeでは **capture単体で9.0s** かかった):

| モード | 4step | 8step |
|---|---|---|
| t2av | 16.12s (3.20x) | 28.75s (5.70x) |
| a2v | 16.79s (3.33x) | 29.01s (5.75x) |

- **リアルタイム(1.0x)には遠く、品質重視の単発生成専用の領域**。ばらつきは±0.2s未満と安定
- a2v の上乗せは 4step +0.7s / 8step +0.3s(グリッドの「平均+0.15s」よりやや大きいが同傾向)
- VRAM は同居プロセス込みで GPU 全体 39.8GB / 48GB — 48GB 級で問題なく通る
- PRO 6000 の見積もり式(24fps へ 121/81 補正)との比較から、**PRO 5000 は概ね 1.3〜1.5 倍遅い**というスケーリングがこの大 shape でも維持される

## 読み方・派生知見

- **a2v の上乗せは t2av 比 平均 +0.15s(中央値 +0.06s)のみ**。ただし t2av で 0.9x 台後半の境界セルは a2v で 1.0x 超過へ転落する(4step: 768×448@24 / 768×480@24 / 768×576@20)
- **a2v 実用上限(4step)**: 16fps = 832×640・960×544 / 20fps = 768×512 / 24fps = 704×416
- 生成時間は画素数にほぼ線形。見積もり式(16fps・81f): 4step **t ≈ 0.79s + 7.9µs/画素**、8step **t ≈ 0.18s + 14.9µs/画素**(〜35万画素まで)
- **fps=16 の列は速度データとしてのみ有効**。品質は 4.0 秒(64f)周期のモーション揺らぎが構造的に出るため運用 NG。**リアルタイム運用は 20fps 推奨**(詳細は acceleration-report の「fps=16 は品質NG」)
- 計測の罠: `LTX25_CUDA_GRAPH_MAX_CAPTURES`(既定8)を超えた shape は黙って eager にフォールバックし遅い値が出る。解像度スイープでは shape 数以上へ引き上げ、ログの `max_captures reached` を確認すること
- a2v は音声トークン数が異なるため CUDA Graph の capture キーが t2av と別。セッション初回クリップは capture 費で遅い
