# 生成AI推論の低VRAM化 技術解説 — 22Bの動画モデルを32GBに収めるまで

この文書は、LTX-2.5(22B DiT)の「全常駐リアルタイム構成」を48GB級から32GB級GPUへ収めるために使った低VRAM化技術を、他のモデルや推論サーバにも応用できる形で解説したものです。速度側の対になる文書は[生成AI推論を速くするための設計ノート](optimization-techniques.md)、LTX-2.5固有の経緯と実測は[高速化の全記録](acceleration-report-20260910.md)を参照してください。

到達点を先に示します(すべて実測。空きVRAMを31GB=ヘッドレスRTX 5090相当に制限したテスト):

| 段階 | 常駐 | 結果 |
|---|---|---|
| 出発点(全常駐 `nvfp4-fast`) | 約32.5GB | 空き31GBでは**ロード段階でOOM** |
| model offload(比較対象) | ピーク22.2GB | 動くが1チャンク約15秒=実時間の3倍で**リアルタイム不成立** |
| 手法1〜2適用 | 28.8GB | 朗読は完走、**会話でOOM**(多shape) |
| +手法4(断片化回収) | 28.8GB | 朗読完走、会話は**CUDA Graph併用時にOOM** |
| +手法3(TE層ストリーミング) | **23.6GB** | **会話・CUDA Graph有効・ピーク27.1GB**で全チャンク成功 |

重要なのは、model offloadという「一般解」がリアルタイム用途では使えない(重みがPCIeを毎回往復して3倍遅くなる)ことです。低VRAM化には「速度を犠牲にする方法」と「速度を保つ方法」があり、この文書は後者だけを扱います。

---

## 1. まずVRAMを解剖する

「VRAMが足りない」は一枚岩の問題ではありません。PyTorchのOOMメッセージは実は内訳を全部教えてくれます。今回実際に出たメッセージから:

```
Tried to allocate 364.00 MiB. GPU 0 has a total capacity of 47.26 GiB of which
215.19 MiB is free. ... this process has 30.87 GiB memory in use. Of the
allocated memory 29.06 GiB is allocated by PyTorch, with 910.24 MiB allocated
in private pools (e.g., CUDA Graphs), and 1.33 GiB is reserved by PyTorch
but unallocated.
```

ここから読み取れる区分は5つあります。

1. **重み(常駐)** — モデルパラメータ。最大の塊で、削減の主戦場。
2. **活性化・ワークスペース(一時)** — forward中だけ生きるテンソルとcuBLAS等の作業領域。「Tried to allocate 364MiB」のような失敗は、たいてい新しいshapeのワークスペース確保。
3. **CUDA Graphのprivate pool** — captureしたグラフが保持する専用領域(上の例で910MB)。**captureしたshapeの数だけ単調に増え、解放されない。**
4. **reserved but unallocated** — PyTorchが確保したが使っていない断片(上の例で1.33GB)。アロケータの断片化で、限界付近ではこれが命取りになる。
5. **PyTorch外** — CUDAコンテキスト、cuDNN/cuBLASハンドル等(上の例で30.87−29.06≈1.8GB)。

対策は区分ごとに別物です。1には「載せない・軽くする・流す」、3には「captureを制御する」、4には「アロケータ設定」。これを混同して「とにかく量子化」に走ると、効かない場所を削って効く場所を見逃します。

## 2. 手法1: 使わないものを載せない(−1.2GB)

最も単純で、最も見逃されがちな手法です。

LTX-2.5サーバは latent upsampler(950MB)と temporal upsampler(250MB)を起動時に無条件でGPUへ載せていました。しかしリアルタイム用途のリクエストは常に `upscale: false` — **一度もforwardされないモジュールが1.2GB常駐していた**のです。

やることは3つだけです。

1. ロードを設定フラグで条件分岐する(`LTX25_LOAD_UPSAMPLERS=0`)
2. 未ロード時にその機能が要求されたら、**明確なエラーを返す**(黙って壊れない)
3. 依存する別経路がないか確認する(今回はt2iの品質パイプラインもupsamplerを使っていたため、そちらにもガードが必要だった)

自分のサーバで「実は使っていないもの」を見つける方法は単純で、各コンポーネントの使用箇所をgrepし、リクエストパラメータの条件と突き合わせるだけです。5分の調査で1.2GBは、この文書の中で最も費用対効果が高い作業です。

## 3. 手法2: 量子化の死角を突く(−1.9GB+一時−0.5GB)

「テキストエンコーダはbnbで4bit量子化済みだからもう軽い」— これが思い込みでした。実際にチェックポイントのsafetensorsヘッダをテンソル単位で集計すると:

| 部位 | サイズ | 精度 |
|---|---|---|
| 言語モデル本体(Linear層) | 5.71GiB | NF4(量子化済み) |
| **埋め込みテーブル** [262144×3840] | **1.88GiB** | **bf16(量子化されていない)** |
| vision tower | 0.04GiB | — |

**bitsandbytesの4bit量子化はLinear層だけが対象**で、`nn.Embedding`は素通りします。語彙26万×隠れ3840の埋め込みテーブルがbf16のままGPUに常駐していました。

### 3.1 埋め込みテーブルはCPUに置ける

埋め込みは行列演算ではなく**テーブル参照**です。1024トークンのプロンプトが必要とするのは1.88GBのうち1024行分(約7.5MB)だけ。そこで埋め込みモジュールのforwardを差し替えます:

```python
orig_forward = embed.forward          # クラスのforward(gather + スケール乗算)
def bridged_forward(input_ids):
    return orig_forward(input_ids.to("cpu")).to(input_ids.device)
embed.to("cpu")
embed.forward = bridged_forward
```

インデックスをCPUへ送り、CPUでgatherして、結果だけGPUへ返す。転送は毎回7.5MBで、実測の速度影響はゼロでした。**出力はGPU実行とbit完全一致**です(gatherは値のコピーであり、スケール乗算のbf16丸めもCPU/CUDAで同一でした — これは仮定せず実測で確認しています)。

### 3.2 罠: 「きれいな設計」の方が壊れる

最初の設計案は「inputs_embedsを自前で計算してモデルに渡す」でした。transformersのforwardは`inputs_embeds`を正式にサポートしているので、一見こちらが筋が良い。しかしソースを読むと、`input_ids`を渡さない経路ではマルチモーダルトークンの判定が「**埋め込みベクトルとの比較**」に切り替わり、その比較のために`get_input_embeddings()(cuda上のインデックス)`が呼ばれます。埋め込みをCPUへ置いた瞬間、デバイス不一致で壊れる。

モジュールのforward差し替え方式なら、この隠れた参照経路も含めて**モデル内部の全呼び出しが無変更で動きます**。教訓: 重みの置き場所を変えるときは、そのテンソルへの参照経路をソースで全部洗うこと。「主経路が動く」ことは「全経路が動く」ことを意味しません。

### 3.3 ついでに消える無駄: 全トークンlogits

このモデルを「テキストエンコーダ」として使うとき、読むのは隠れ状態だけです。ところが`ForConditionalGeneration.forward`は`logits_to_keep=0`(=全トークン)で`lm_head(hidden_states)`を必ず計算します。1024トークン×語彙262144のbf16で**約0.5GBの一時テンソルが毎回作られて捨てられていた**。

text_encoder.forwardを「内部モデルを同一引数で呼んで出力をそのまま返す」薄いラッパーに差し替えて、lm_headを経由しないようにしました。なおlm_headの重みは埋め込みテーブルとtied(同一テンソル)なので、重み側の追加節約はゼロです — tied weightは「片方を動かすともう片方も動く」ことも含めて把握しておく必要があります。

## 4. 手法3: 窓付き層ストリーミング(−5.0GB、本命)

残る大物は言語モデル本体(NF4で5.7GB)です。これは生成のたびに全層が計算に使われるので「載せない」はできません。しかし**全層が同時に必要なわけではない** — 層は順番に実行されます。そこで、重みをpinned host memoryに常駐させ、エンコード中だけ層単位でGPUへ流します。

### 4.1 成立条件の算数を先にやる

ストリーミングが速度を保てるかは、実装前に計算で見積もれます。

- 層あたりの計算時間: エンコード全体0.21秒 ÷ 48層 ≈ **4.4ms**
- 層あたりの転送時間: 5.7GB ÷ 48層 ≈ 120MB、pinned転送 ~50GB/s で ≈ **2.4ms**

**転送 < 計算** なので、1層先を先読みしておけば転送は計算の陰に完全に隠れます。この不等式が逆(転送の方が長い)なら、ストリーミングは必ず遅くなり、この手法は成立しません。モデルと接続(PCIe世代)によって答えが変わるので、必ず自分の環境で分子分母を測ってください。

### 4.2 既製品がなぜ遅かったか

diffusersには`apply_group_offloading`という同目的の機構があり、まずそれを試しました(自作の前に既製品を測るのは常に正しい)。結果:

| 構成 | エンコード時間 | 問題 |
|---|---|---|
| 全常駐(基準) | 0.213s | — |
| diffusers, use_stream=True | 1.25s | stream使用時は**1層=1グループが強制**され、48グループ×フック固定費~22ms |
| diffusers, use_stream=False | 2.2s | **pinnedにならず**、pageable転送(~4GB/s)に落ちる |
| **自作(窓付き先読み)** | **0.369s(+0.156s)** | — |

diffusersの実装が悪いのではなく、汎用フック機構の固定費(グループごとのPython処理・同期)が、48回×22msという形でこのワークロードには重すぎた、という話です。**フック1回の固定費 × グループ数** という積を見積もると、既製品で足りるかが事前に分かります。

### 4.3 自作ストリーマの設計(約100行)

方式はシンプルですが、正しく動かすための要点が4つあります。

**(1) 何を動かすかの列挙 — bnbのquant_stateを忘れない**

量子化モデルの層を動かすとき、`named_parameters()`と`named_buffers()`だけでは不足です。bitsandbytesの`Params4bit`は量子化メタデータ(`quant_state.absmax`など)を**パラメータでもバッファでもない属性テンソル**として持っています。これを一緒に動かさないと、重みはGPU・スケールはCPUという食い違いで壊れます:

```python
for _, p in module.named_parameters(recurse=True):
    items.append((p, "data", p.data))
    qs = getattr(p, "quant_state", None)
    if qs is not None:
        for attr in ("absmax", "code", "offset"):
            t = getattr(qs, attr, None)
            if isinstance(t, torch.Tensor):
                items.append((qs, attr, t))
```

**(2) 同期はstream+eventで、層単位に**

コピー専用streamで層iのテンソル群を`non_blocking=True`で転送し、層iのeventをrecord。計算側は各層のforward_pre_hookで**自層のeventだけ**をwaitします。これで「層0の計算」と「層1の転送」が並走します。

**(3) アロケータの早期再利用を防ぐ — record_stream**

コピーstreamで確保したテンソルを計算streamで使い、使い終わったら参照を切って解放する — このパターンには罠があります。PyTorchのキャッシングアロケータは「参照が切れたメモリ」を即座に再利用しますが、**別streamでまだ実行中のカーネルがそのメモリを読んでいる**可能性があります。対策は使用開始時に`tensor.record_stream(計算stream)`を打つこと。これでアロケータは計算streamがそこを通過するまで再利用を遅延します。これを忘れると「たまに壊れる」再現困難なバグになります。

**(4) 復元はポインタ差し戻しのみ — D2Hコピーはゼロ**

推論では重みは変化しません。だからエンコード終了時にやることは、保存しておいたpinned CPUテンソルへ`param.data`を**指し直すだけ**です。GPU→CPUの書き戻しコピーは一切発生しません。ここに気づくと、offloadの往復コストの半分が最初から存在しないことが分かります。

### 4.4 罠: 全深度先読みは本末転倒

最初の実装は「全48層のコピーを先頭で一括投入」でした。速度は+0.166sで良好、しかし**エンコードの瞬間に全層(4.35GB)がGPUに揃ってしまい、常駐を削った意味が半減**します。先読みを窓(window=2)に制限し、層iの完了後に層iを手放して層i+2を投入する形に直して、エンコード中の追加VRAMを窓2層分+活性化(計~1.5GB)に抑えました。窓を4や8に広げても速度は変わりません(4.1の不等式が窓2で既に満たされているため)。

### 4.5 検証: bit一致を「2回連続」で確認する

正しさの検証は全常駐ベースラインとの出力比較ですが、**必ず2回連続で実行して両方を比較**してください。1回目はストリーミング自体の正しさを、**2回目は復元経路の正しさ**(ポインタ差し戻し後の状態から再度正しく流せるか)を検証しています。1回だけの検証では、状態を壊しながら正しい出力を出すバグを見逃します。

## 5. 手法4: アロケータの断片化を回収する(−1.3〜1.6GB)

手法1〜2適用後の朗読テストは28.8GBで完走しました。ところが**実アプリの会話は境界OOM** — 単一shapeの合成テストと実アプリの差がここで出ます。

実アプリは待機動画・発話アンカー・ターン先頭の低解像度チャンク・本番チャンクと**複数のテンソルshapeを行き来**します。shapeが変わるたびにアロケータは別サイズのブロックを確保し、解放されたブロックはサイズが合わず再利用されにくい。結果が「reserved but unallocated 1.33GB」— 確保済みなのに使えない断片です。

対策は1行です:

```
PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True
```

セグメントを可変長にして断片を継ぎ足し利用できるようにする設定で、多shape実運用では実質必須でした。教訓として大きいのは、**境界VRAMの検証は合成ベンチマークではなく実アプリのshape分布で行う**こと。合成テストの28.8GBという数字は正しかったのに、実運用では通らなかったのです。

## 6. CUDA Graphとの相互作用 — 一度負けて、取り返す

速度側の主力であるCUDA Graph(denoiseのcapture/replay)は、VRAM側では厄介な相手です。

- captureしたshapeごとにprivate poolを保持し、**単調に増えて解放されない**
- 新しいshapeが来るたびにcapture(warmup+ワークスペース確保)が走り、**一時的なスパイク**が乗る

会話モードで実際に起きたのは次の症状でした: capture済みshapeのチャンクは成功し、**新shapeのチャンクだけが交互に失敗する**(364MBのワークスペース確保がOOM)。この「replayだけ成功する」パターンはgraph poolの逼迫に特有の症状なので、見たらVRAMの区分3を疑ってください。

このとき一度「32GBではgraph無効」と結論しました(この解像度帯のgraph利得は3.5s vs 3.4sと僅かだったため、正しいトレードオフでした)。しかし手法3で5GBの余裕が生まれた後に再挑戦し、**graph有効のまま会話E2Eがピーク27.1GBで完走**。最終構成はgraph有効です。

一般化すると: **「最速の構成」と「メモリが単調に増えない構成」は境界VRAMでは対立する**。余裕が数GBを切ったらまず後者を選び、削減で余裕を作ってから前者を取り戻す、という順序が安全です。

## 7. 測定の方法論

この作業の半分は測定でした。使った道具と原則を列挙します。

**バラスト法** — ダミーテンソルでVRAMを確保し、空き容量を目標カードと同じに制限する。実物の32GBカードがなくても48GB機で「空き31GB」を再現できます。~15行のスクリプトで済み、本プロジェクトの全ての「5090相当」実測はこの方法です。注意: 制限するのは「空き容量」であって、断片化パターンやコンテキストサイズまでは再現しません。

**プロセス単位のピーク計測** — `nvidia-smi --query-compute-apps`を0.5秒間隔でポーリングし、対象プロセスの最大値を取る。アプリ内の`torch.cuda.max_memory_allocated()`はPyTorch管理分しか見えないので、両方を記録して差(コンテキスト等)も把握します。今回の実測では常に1.5〜2GBの差がありました。

**bit一致検証は同一プロセス内で** — 今回の副産物として、nvfp4構成は**プロセスを再起動すると同一seedでも出力が変わる**(PSNR 27dB級の軌道分岐)ことが分かりました。同一プロセス内では完全決定論(framemd5一致)です。新機能のbit検証をプロセスをまたいで行うと、この非決定性を新機能のバグと誤認します — 実際に一度誤認しかけ、対照実験(同一構成でプロセスだけ再起動)で切り分けました。

**OOMメッセージを読み切る** — 1章の区分を使えば、OOMメッセージ1つで「何を削るべきか」の当たりが付きます。「Tried to allocate 364MiB / free 215MiB / private pools 910MB / reserved-unallocated 1.33GB」なら、犯人は常駐ではなくpoolと断片化です。

最終構成(`nvfp4-32gb`プリセット)の内訳:

| 対策 | 削減 | 速度コスト |
|---|---|---|
| 手法1: upsampler非ロード | −1.2GB 常駐 | ゼロ(未使用機能の無効化) |
| 手法2: embed CPU化+logits除去 | −1.9GB 常駐、−0.5GB 一時 | ゼロ(実測差なし) |

検証済みの動作点(空き31GB制限、TTSは別GPU、LLMは別ホスト): 会話7チャンク連続・全チャンク成功・ピーク27.1GB・CUDA Graph有効。

## 9. 適用チェックリスト(他モデルへの一般化)

1. OOMメッセージで区分(重み/一時/pool/断片)を特定したか
2. 一度もforwardされないモジュールがGPUにいないか(使用箇所をgrep)
3. 量子化の対象外(embedding、norm、head)にbf16の大物が残っていないか
4. tied weightの共有関係を把握したか
5. テーブル参照系(embedding)はCPU化候補 — ただし参照経路をソースで全部洗う
6. 使わない出力(logits等)を計算していないか
7. ストリーミングは「層あたり転送 < 層あたり計算」を先に計算で確認
8. 既製offload機構は「フック固定費×グループ数」を測ってから採否判断
9. 量子化ライブラリのメタデータテンソル(quant_state等)を移動対象に含めたか
10. record_streamでアロケータの早期再利用を防いだか
11. bit一致は2回連続・同一プロセス内で検証したか
12. 最終検証は合成ジョブではなく実アプリのshape分布で行ったか
